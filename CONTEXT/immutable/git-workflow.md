# Git workflow

Перед началом любой работы обязательно создать feature-ветку от актуального `dev`.

## Начало работы

1. Проверить состояние текущего рабочего дерева.
2. Переключиться на `dev`.
3. Получить актуальное состояние `dev` из remote:
   - `git fetch`;
   - обновить `dev` только fast-forward'ом.
4. Убедиться, что `dev` чистый и соответствует remote.
5. Создать новую ветку:

   `feature-<hash>-begin--<human_name>`

   где:
   - `<hash>` — уникальный короткий идентификатор работы;
   - `<human_name>` — короткое понятное название задачи в kebab-case.
6. Запушить созданную ветку в remote.
7. Только после этого начинать изменять код.

## Завершение работы

После полного завершения задачи:

1. Проверить состояние рабочего дерева.
2. Выполнить все необходимые тесты и проверки.
3. Убедиться, что Wiki и другая проектная документация актуальны.
4. Переименовать текущую ветку:

   `feature-<hash>-begin--<human_name>`

   →

   `feature-<hash>-end--<human_name>`

5. Запушить `feature-<hash>-end--<human_name>` в remote.
6. Создать Pull Request:

   `feature-<hash>-end--<human_name>` → `dev`
7. Не выполнять merge самостоятельно, если это явно не запрошено.

## Правила

- Никогда не начинать работу непосредственно в `dev`.
- Начинать создавать ветку можно только при чистом `dev`.
- Feature-ветка всегда создаётся от актуального `dev`.
- Начальная ветка обязательно должна быть запушена до начала разработки.
- Не удалять `*-begin-*` ветку до завершения работы.
- Завершённая ветка всегда имеет суффикс `-end--<human_name>`.
- PR всегда направляется в `dev`.
- Если рабочая ветка уже существует, не создавать новую без явного решения пользователя.
- Не создавать PR до завершения всех изменений и проверок.
- Не выполнять merge самостоятельно.

# Работа с проектом

## Перед началом работы

Перед началом реализации необходимо восстановить контекст проекта.

Необходимо ознакомиться с:

1. Общими правилами проекта.
2. Архитектурой проекта.
3. Контрактами и протоколами, относящимися к задаче.
4. Актуальным состоянием Wiki.
5. Issue и всеми его комментариями.
6. Комментариями связанных Pull Request.
7. Другой документацией, непосредственно относящейся к задаче.

Нельзя делать вывод о текущем состоянии проекта только на основании описания Issue.

## Анализ задачи

Перед изменением кода необходимо определить:

- что именно требуется изменить;
- какие компоненты затрагиваются;
- какие существующие контракты должны быть сохранены;
- какие контракты или архитектурные решения изменяются;
- какие тесты должны быть добавлены или изменены;
- требуется ли изменение Wiki.

Если для реализации требуется изменить архитектуру, контракт или публичное поведение системы, это должно быть явно отражено в Wiki.

## Реализация

Изменения должны выполняться последовательно и минимально необходимым объёмом.

Не следует изменять существующее поведение, архитектуру или контракты, если это не требуется задачей.

Новые решения должны соответствовать существующей архитектуре проекта, если задача явно не требует её изменения.

## Проверка

Перед завершением работы необходимо:

1. Выполнить тесты, относящиеся к изменённому коду.
2. Выполнить необходимые интеграционные тесты.
3. Выполнить общие проверки проекта, если они предусмотрены.
4. Исправить обнаруженные проблемы.
5. Повторно выполнить проверки после исправлений.

PR нельзя создавать при наличии известных неисправностей, относящихся к выполненной задаче.

# Работа с Wiki

Wiki является частью контекста проекта и должна содержать актуальное состояние системы.

## Перед началом итерации

Перед началом работы необходимо прочитать актуальный Wiki-контекст, относящийся к задаче.

Wiki используется для восстановления контекста между отдельными итерациями разработки.

## Во время работы

Если в процессе работы получена новая информация, которая имеет значение для текущего тикета, она должна быть отражена в Wiki.

К такой информации относятся:

- архитектурные решения;
- изменения архитектуры;
- изменения контрактов;
- зависимости между компонентами;
- важные ограничения;
- результаты исследования;
- принятые технические решения;
- обнаруженные особенности существующей реализации;
- решения, которые необходимо учитывать в следующих итерациях.

Не следует записывать в Wiki временные детали, не имеющие значения для дальнейшей работы.

## Перед завершением итерации

Перед завершением каждой итерации необходимо:

1. Обновить Wiki актуальной информацией.
2. Зафиксировать принятые решения.
3. Зафиксировать изменения архитектуры и контрактов.
4. Удалить или исправить устаревшую информацию.
5. Убедиться, что следующая итерация сможет восстановить необходимый контекст из Wiki.

Wiki не должна содержать заведомо устаревшие сведения.

## Связь Issue, PR и Wiki

**Issue** описывает задачу и её текущий рабочий процесс.

**Wiki** содержит долговременный технический контекст и знания о проекте.

**PR** содержит конкретный набор изменений, реализующий задачу.

Изменение должно быть отражено в Wiki, если оно изменяет долговременное понимание проекта.

Не следует переносить в Wiki весь текст Issue или PR.

## Правило актуальности

Wiki должна описывать **текущее состояние проекта**, а не историю всех изменений.

Если новое решение отменяет старое, Wiki должна быть обновлена так, чтобы в ней осталось актуальное решение, а не оба противоречащих друг другу варианта.

# Завершение задачи

Задача считается полностью завершённой только после выполнения всех условий:

- код реализован;
- тесты пройдены;
- необходимые проверки пройдены;
- Wiki актуальна;
- feature-ветка переименована в `*-end--*`;
- ветка `*-end--*` запушена в remote;
- создан PR в `dev`.

Merge выполняется только по явному указанию пользователя.
